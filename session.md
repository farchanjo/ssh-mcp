### Update plan (in order)

1. `russh` 0.60.3 to 0.65.4 with `russh-sftp` 2.4.0 to 4.0.0. `cargo audit` on
   2026-11-21 reports RUSTSEC-2026-0492, -0493, -0494 and -0495 on `russh`
   0.60.3; RUSTSEC-2023-0071 (`rsa`) and RUSTSEC-2026-0387 (`crypto-bigint`)
   arrive through it. **Outcome, measured 2026-11-22 in feature 001
   (`doc/arch/sdd/001-russh-advisory-upgrade/`):** the manifest asks for the
   0.65 and 4 lines, one `cargo update -p russh -p russh-sftp` resolves `russh
   0.65.4` and `russh-sftp 4.0.0`, and `cargo audit` on that set names no
   advisory for `russh`, `rsa` or `crypto-bigint`. The same change adapted
   `check_server_key` to the new trait argument, rejects a host certificate
   instead of trusting its key, states the offered host-certificate list empty,
   and repaired the channel-open retry classifier to read the typed error (a
   `ResourceShortage` refusal now retries; a peer-supplied `reason` string no
   longer decides one). Not landed with it: the lockfile stays untracked, so
   `pin.cargo.lockfile-missing` and item 6 stand, and RUSTSEC-2026-0462 on
   `rmcp 1.8.0` with the unmaintained `chrono 0.4.45` warning stay open under
   item 2.
2. `rmcp` 1.8.0 to 3.11.0 (RUSTSEC-2026-0462, fixed in 3.9.0), keeping the
   `initialize` handshake of the earlier protocol revisions. Support for MCP
   revision 2026-07-28 is deferred: it removes `initialize`, HTTP sessions and
   `resources/subscribe`, and creates a handler per request, while this server
   builds all of its state inside the handler (`build_server` in
   `src/composition/prod.rs`). A compile probe of the bump showed 14 errors in
   8 files, of three kinds (model types renamed in 2.0,
   `ResourceUpdatedNotificationParam` no longer built from a struct literal,
   `read_resource` and `get_prompt` returning response enums in 3.0).
   **Outcome, measured 2026-11-22 in feature 002
   (`doc/arch/sdd/002-rmcp-sdk-upgrade/`):** the manifest requires `rmcp`
   3.11, the set resolves `rmcp 3.11.0`, and `cargo audit` reports no
   vulnerability; the `chrono 0.4.45` warning under RUSTSEC-2026-0543 stays.
   The server keeps `initialize`, advertises `2025-11-25` as its ceiling, and
   answers a `2026-07-28` or unknown revision with `2025-11-25`. Not landed
   with it: the lockfile stays untracked (`pin.cargo.lockfile-missing`).
3. Small bumps: `md-5` 0.11, `sha2` 0.11, `base64` 0.23, `tower-http` 0.7.
   **Outcome, measured 2026-11-22 in feature 003
   (`doc/arch/sdd/003-direct-dependency-refresh/`):** the manifest asks for
   the 0.23, 0.11, 0.11 and 0.7 lines, ten packages leave the lock (the
   duplicate `base64` and `sha2` copies and the `digest` 0.10 chain among
   them), and the wire is unchanged, pinned by known-answer tests. The trace
   layer is DEBUG-only and invisible under the default filter; a fixed-length
   response gains one `on_eos` line on `tower-http` 0.7.1, kept because
   `OnEos` receives no response headers. The lockfile stays untracked.
4. Defect fixes (list below).
5. Claude Code channel support in `ssh-mcp-stdio`: metadata-only events
   (command finished, transfer completed, session dropped), opt-in, no remote
   bytes in the event body, no permission relay. A channel server must not
   negotiate revision 2026-07-28, one more reason for item 2's choice.

### 1. Shell-open race fix (functional)

`OpenShellUseCase::execute` and `RusshAdapter::open_shell`'s detached registration
sink both write the shell row. Whichever landed second met `Entry::Occupied`, and
`ssh_shell_open` surfaced `INTERNAL_ERROR: shell <id> already exists` under load.
The new `persist_shell` helper treats an occupied row as success and overwrites it
with the use-case entity (the adapter builds its copy before `apply_overrides`, so
keeping the sink row would persist the default TTL instead of the caller's
override), re-raising only genuine write failures. Scenario 13
(`row_already_written_by_registration_sink_is_not_a_conflict`) pins both halves —
id coexistence and override authority — and fails with the original
`Internal("... already exists")` when the helper is reverted.

  transfer rows stay in the repository for `ssh_transfer_progress` /
